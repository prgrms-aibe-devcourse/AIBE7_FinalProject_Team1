# R10 판매글 AI 요약 자동 최신화

R09의 게시 후 요약 생성에 정보 변경 후 자동 갱신을 연결한다. 요구사항 AI-03의 최신화 안내·결과 교체와 ERD의 제품 버전·판매글 버전·시도 ID 검사를 따른다.

## 연결된 변경과 처리 흐름

| 변경 | 실제 연결 |
|---|---|
| 판매글 제목·설명·가격·등급·사진 수정 | `ListingManagementService.update` → `ListingContentChanged` |
| 제품명·구매일·보증 만료일 정정 | `ProductService.update` → `ProductFactsChanged` |
| 사양·이력 추가·정정·무효·공개 범위 변경 | `ProductFactsChanged` 수신·테스트 완료. 해당 기능의 운영 변경 지점에서 발행하는 연결은 필요 |

수정 트랜잭션의 커밋 뒤 `ListingSummaryRefreshListener`가 별도 트랜잭션으로 최신 버전의 작업을 접수한다. 롤백된 변경은 접수하지 않고 AI 응답을 기다리지 않는다. 접수 장애가 이미 성공한 수정 응답을 오류로 바꾸지 않는다.

기존 요약에 버전 차이가 남은 경우 디스패처가 주기적으로 접수를 복구한다. 미요청 판매글 전체를 일괄 생성하거나 GET 조회로 생성을 접수하지 않는다.

이력·사양 담당 모듈은 변경 트랜잭션 안에서 다음 두 작업을 함께 수행해야 한다.

```java
// 공개 정보·이력 변경과 같은 트랜잭션에서 facts_version을 증가시킨다.
events.publishEvent(new ProductFactsChanged(productId));
```

이 이벤트는 제품 ID만 담으며 사용자 자유 입력·개인정보를 포함하지 않는다. 판매 중·예약 중인 해당 제품의 판매글만 대상으로 하고, 실제 작업 확보 시 현재 소유자와 공개 상태를 다시 검사한다. 현재 제품 수정 API는 사양 변경을 지원하지 않으므로 이번 작업에서 사양 수정 API나 이력 저장 기능을 새로 만든 것은 아니다.

## 화면과 API

기존 `GET /api/v1/listings/{listingId}/summary`와 상세 응답의 `summary`에 `outdated`를 추가한다. 상태 값과 POST 경로는 유지한다.

| 상태 | text와 화면 |
|---|---|
| READY | 최신 검증 결과, `outdated=false` |
| QUEUED / PROCESSING + 이전 요약 | `outdated=true`, 이전 판매 조건 기준임을 표시하고 아래에 최신화 중 안내 |
| FAILED + 이전 요약 | `outdated=true`, 갱신 실패·이전 정보 안내와 판매자 재시도 제공 |
| 이전 문장을 제공할 수 없는 경우 | text 없음. 생성 상태만 표시하며 기본 상세·타임라인 유지 |

이전 문장은 **제품 사실 버전이 그대로인 판매 조건 수정**에만 유지한다. 제품·이력·공개 범위가 바뀌어 제품 버전이 달라지면 이전 문장은 제거한다. 알려진 작성 지침 반복 문장이나 자료 변경 오류 결과도 재사용하지 않는다. 과거 내용을 새 결과로 오해하거나 비공개로 바뀐 정보가 남는 일을 막기 위한 보수적인 처리다.

새 결과를 저장하면 이전 문장을 교체하고 `outdated=false`로 반환한다. 판매 종료·소유권 상실·보관 제품은 이전 요약을 포함한 공개 조회를 차단한다. 화면 이탈·탭 복귀·늦은 HTTP 응답 처리와 textContent 렌더링은 유지한다.

생성 중에는 처음 30회는 2초, 이후 30회는 10초 간격으로 조회한 뒤 수동 상태 확인을 제공한다. 미요청·완료 상태는 15초마다 확인하고, 실패 상태도 재시도 대기 종료와 다른 변경의 자동 접수를 확인한다.

## 중복·실패·재시작 처리

- 자동 갱신은 기본 1,500ms 동안 대기한다. `app.ai.summary.refresh-debounce-ms`로 0~30,000ms 범위에서 설정할 수 있다. 연속 수정은 마지막 버전과 새로운 시도 ID로 교체한다.
- 이미 실행 대기 목록에 담겼던 이전 시도도 DB 상태·시도 ID·실행 가능 시각을 다시 검사한다. 완료 시 현재 제품·판매글 버전과 전체 공개 자료 지문을 검사한다.
- 다른 AI 작업 때문에 Redis 실행 제한에 걸리면 공급자를 호출하기 전에 같은 시도를 DB 대기열로 돌린다. 공급자 요청 후의 실패·429·검증 실패는 자동 재호출하지 않는다.
- 실행 제한 대기에도 최초 접수 시각을 유지한다. QUEUED는 최초 접수 후 5분, PROCESSING은 모델 기한+60초를 넘으면 실패로 복구한다. 같은 버전의 실패를 무한 자동 생성하지 않는다.
- 기존 요약이 없어도 판매글 수정 이벤트는 첫 생성을 접수할 수 있다. 이벤트 접수를 놓친 미요청 판매글은 버전 비교로 찾을 기준이 없으므로 판매자의 명시적 생성 요청이 필요하다.

## DB 변경

새 `V2026102706__support_listing_summary_refresh.sql`만 추가한다. 기존 마이그레이션은 수정하지 않는다.

- `summary_requested_at`: 실행 제한 대기와 별개로 유지하는 최초 접수 시각.
- `summary_available_at`: 짧은 수정 대기·Redis 실행 제한 후 다음 실행이 가능한 시각.
- 기존 상태의 시각은 `summary_updated_at`으로 채운다. 요약·시도 ID·판매글·초안·사진을 보존한다.
- CHECK는 갱신 대기·처리·실패 중 이전 요약 보관을 허용하되 빈 요약·부분 상태·오류 코드가 잘못된 조합은 거부한다.
- 갱신 중 `summary_source_*_version`은 현재 시도의 대상 버전이다. text가 이전 문장인지 여부는 응답의 `outdated`로 구분한다.

## 검증

- 전체 `spotlessCheck test build`: 517건 중 494건 통과, 환경 조건으로 23건 제외, 실패·오류 0건.
- 새로 만든 전용 PostgreSQL 테스트 DB에서도 `ListingSummaryHttpTest` 34건 모두 통과했다. 테스트가 만든 스키마와 전용 DB는 종료 후 정리했으며 사용자 DB를 초기화하지 않았다.
- HTTP에서 수정 커밋 후 자동 접수·롤백 시 미접수, 연속 수정의 최신 버전 선택, 실행 중 추가 수정과 늦은 결과 차단을 확인했다.
- 이전 요약 유지·갱신 실패·판매자 재시도, 제품 정보 정정 시 이전 내용 제거, 예약 중 이력 변경 이벤트, 종료·소유권 상실 시 차단을 확인했다.
- Redis 대기 시 외부 미호출·같은 시도 유지·실행 가능 시각 준수·최초 접수 시각 기준 만료와 공급자 오류 자동 재호출 방지를 확인했다.
- 파일 H2의 R09 READY·QUEUED 데이터에 새 Flyway를 적용해 요약·시도 ID·접수 시각 보존과 CHECK 동작을 확인했다.
- 별도 메모리 DB·AI 대역 서버에서 화면 수정 → 이전 문장과 최신화 중 안내 → 최신 등급 요약 교체, 실패 안내와 재시도 대기·활성화를 확인했다. 실제 Gemini 결과 품질 검증은 R09 기록과 구분한다.
- 기존 18081 시연 DB를 백업한 뒤 새 빌드를 실행했다. 33번 요약의 READY·기존 내용 유지·`outdated=false`를 확인했다.
- 사용자가 33번 판매글의 등급을 3등급으로 수정한 뒤 실제 Gemini 새 요약의 3등급 반영을 화면에서 확인했다. 이후 상세 API 재조회에서 내용 버전 1·등급 3·요약 READY·`outdated=false`와 요약 문장의 3등급 반영을 확인했다.

운영 이력 어댑터와 실제 이력·사양 저장 지점의 이벤트 발행 연결은 해당 모듈과 맞춰야 한다. 모든 R10 외부 연동이 끝났다고 간주하지 않는다. R09 품질 보완 PR #44가 병합된 main을 기반으로 한다.

## 직접 확인하기

1. 18081의 기존 판매글 상세에서 `내 판매글 관리`를 연다.
2. 상태 등급이나 판매 조건을 수정하고 저장한다.
3. 별도 생성 버튼을 누르지 않아도 이전 요약과 최신화 중 안내가 나오는지 확인한다.
4. 완료 후 수정한 등급이 반영된 새 요약으로 교체되는지 확인한다. 빠르게 완료되면 중간 표시는 짧게 지나갈 수 있다.
5. 새로고침해 최신 요약이 유지되는지 확인한다.
