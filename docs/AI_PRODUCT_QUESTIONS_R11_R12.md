# 제품 이력 Q&A — 실제 조회·답변·근거

요구사항 `AI-04~AI-08`을 따른다. 현재 소유자의 제품과 로그인 회원에게 공개된 ACTIVE/RESERVED 판매글에서 등록된 사양·보증·누적 이력으로 질문에 답한다. 기존 `/api/v1/ai/ask`의 고정 안내 응답과 별도 경로이며, 가격 평가·구매 추천·품질·안전성·정품 판정은 제공하지 않는다.

## API와 화면

| 경로 | 권한 |
|---|---|
| `POST /api/v1/products/{productId}/ai/questions` | 현재 소유자. 판매글 종료 후에도 허용 |
| `POST /api/v1/listings/{listingId}/ai/questions` | 로그인 회원. ACTIVE/RESERVED이며 게시자가 현재 소유자인 글만 허용 |

요청은 `{"question":"현재 메모리 사양을 알려줘"}`이며, 공백을 제외한 질문이 필요하고 최대 1,000자다. 사용자 ID·도구 이름·모델·공급자 URL은 클라이언트가 지정하지 않는다. JWT·쿠키 인증 및 기존 CSRF 검증을 적용한다.

성공 응답의 `data`는 `answer`, `sources`, `factsVersion`, `contentVersion`, `generatedAt`, `sample`이다. 내 제품 응답의 `contentVersion`은 null이다. 근거는 서버가 조립한 `key`, `type`, `label`, `facts`로 반환하며, 사양의 실제 값, 보증 만료일·조회 기준일, 이력 번호·유형·발생일·상태·정정·이전 소유자·세부 검토 여부를 종류에 맞춰 표시한다. 미검토 이력의 본문이나 무효 이력의 상세 내용은 포함하지 않는다.

내 제품의 제품 여권 화면과 판매글 상세에 `제품 이력에 질문하기`를 표시한다. 질문 예시는 입력만 채우며 `질문하기`를 눌러야 호출한다. 답변 아래의 근거를 펼쳐 실제 기록을 확인한다. 실패·자료 변경 때는 질문을 유지하고 사용자가 다시 시도하며, 429는 `Retry-After` 동안 제출을 막는다. 페이지 이탈·제품 변경·계정 전환 시 입력·답변과 진행 중 요청을 정리한다. 질문·대화·답변을 DB나 브라우저 저장소에 저장하지 않는다.

## 호출 흐름

1. `ProductQuestionController`가 인증된 사용자의 ID와 고정된 제품/판매글 범위를 서비스에 전달한다.
2. `ProductQuestionSource.capture`가 제품→판매글 순서로 잠그고 현재 소유권·공개 상태를 확인한다. `ListingSuggestionSource`의 허용 목록·전체 이력·48KB 제한을 재사용하고 제품/판매글 버전, 공개 상태, 자료 지문과 조회 기준일을 기억한다.
3. 범위 밖 판단·개인정보 요청은 권한 검사 후 정해진 안내로 답한다. 실제 생성은 기존 Redis의 회원별 동시 실행·분당 요청·전체 요청 제한을 공유한다.
4. Gemini 첫 요청은 질문과 함수 정의만 전달한다. 모델은 `get_product_specs`, `get_product_warranty`, `get_product_history`를 선택할 수 있다. 모든 함수 인자는 빈 객체이며 제품·판매글·사용자 ID나 쓰기 함수 요청은 거부한다.
5. 선택한 함수는 권한과 자료를 다시 검사한 뒤 해당 범위의 실제 조회 결과만 반환한다. 같은 함수의 반복 호출이나 최대 세 개를 넘는 요청은 거부한다. 도구 결과는 지시문이 아닌 자료로 취급한다.
6. 두 번째 모델 요청에서 함수 결과를 전달해 `answer`와 `sourceKeys`를 받는다. 첫 응답의 전체 parts와 thought signature, 함수 호출 ID를 보존하고 추가 도구 호출은 허용하지 않는다. 두 왕복과 도구 조회는 기존 AI 제한 시간 하나를 공유한다.
7. 모델의 근거 키가 실제 전달한 자료에 존재하는지 검사하고 가짜 근거는 거부한다. 모델이 읽은 이력에 무효 기록이 있으면 모델 문장을 사용하지 않고 `ProductQuestionGroundedAnswer`가 조회한 사양·보증 만료일·이력 날짜·유형·상태로 답변을 구성한다. 모델이 무효 근거를 인용하지 않아도 무효 안내를 유지하고 자유 입력 본문은 재사용하지 않는다. 근거는 최대 20개이며 일부만 표시하면 전체 이력 확인을 안내한다. 그 외에 근거가 없으면 모델의 단정 대신 `등록된 기록으로는 확인할 수 없다`는 고정 안내를 반환한다. 최종 문구에도 숫자·개인정보·명백한 금지 표현 검사를 적용한다.
8. 응답 직전 권한·소유권·제품 버전·판매글 버전·전체 자료 지문을 다시 확인한다. 종료·소유권 상실은 404, 자료 변경은 409 `AI_005`로 차단한다. 외부 AI를 기다리는 동안 DB 트랜잭션·행 잠금을 유지하지 않는다.

함수 호출 형식은 [Gemini GenerateContent REST](https://ai.google.dev/api/generate-content)와 [함수 호출 안내](https://ai.google.dev/gemini-api/docs/function-calling)를 참고한다. 서버의 조회 도구는 기존 서비스·저장소를 직접 사용하며, 모델이 임의의 HTTP 주소나 SQL을 실행하지 않는다.

## 공개 자료 경계와 제한

- 내 제품 Q&A도 현재는 판매 AI와 같은 보수적인 허용 목록을 사용한다. 시리얼·비용·증빙·OCR·채팅·사적인 제품 별칭과 미검토 자유 입력은 외부 모델에 보내지 않는다. 소유자라는 이유로 모든 비공개 데이터를 AI에 전달하지 않는다.
- 정식 이력 Reader가 아직 본문을 공개 검토하지 않은 기록은 유형·날짜·유효/무효·정정 표시만 설명한다. 미검토 본문에 적은 교체 부품·수리 내용을 AI가 읽었다고 표현하지 않는다.
- 등록된 보증 만료일이 없으면 보증을 확인할 수 없다. 보증 조건 문서는 조회하지 않으며, 구매 후 경과 기간을 사용 기간으로 바꾸지 않는다.
- 근거 키·ID와 숫자 검사는 의미 전체의 정확성을 보장하지 않는다. 실제 사용자는 답변에 표시된 근거와 전체 이력을 함께 확인한다.
- 최대 세 개의 조회 도구와 두 번의 모델 요청으로 제한한다. 일부 기록을 몰래 제외하지 않으며 입력 크기 초과·원천 미연동은 오류로 구분한다.
- 새 DDL·마이그레이션·의존성은 없다. 정식 이력 Reader는 `LISTING_HISTORY_ENABLED=true`가 필요하다. 모델 설정은 기존 `GEMINI_API_KEY`(또는 `AI_API_KEY`), `AI_MODEL`, `AI_LISTING_ENABLED`, `AI_TIMEOUT_SECONDS`를 사용한다. 키를 코드·질문·로그에 기록하지 않는다.

## 검증

- `spotlessCheck test build`: 전체 871개 중 788개 성공, 환경 조건으로 83개 제외, 실패 0개.
- 새 HTTP 검사 21개는 실제 Spring·JWT·CSRF·정식 이력 Reader·서비스·DB를 사용한다. 모델과 Redis 실행권만 시험 대역이다. 권한·종료·소유권 상실·자료 변경·가짜 근거·무효/미검토·빈 이력·보증·요청 제한을 검사한다.
- 같은 HTTP 검사 21개를 별도 PostgreSQL DB에서도 모두 통과했다. 테스트가 만든 스키마와 DB는 종료 후 제거했다.
- 새 Gemini 전송 검사 14개는 로컬 공급자 HTTP 서버로 실제 함수 요청/결과·서명/호출 ID 보존·허용 목록·인자 거부·반복 거부·최종 JSON·전체 제한 시간을 검사한다. 외부 Gemini를 호출하지 않는다.
- 별도 18082 복제 DB에서 실제 Gemini로 질문했을 때 DB의 16GB 메모리와 같은 답변, 실제 사양 근거, `sample=false`를 확인했다. 특정 응답 성공이며 모든 질문의 정확성을 보장하는 검증은 아니다.
- 실제 브라우저에서 별도 시험 계정으로 판매글 질문→대기 표시→Gemini 답변→사양 근거 펼치기, 빈 이력의 확인 불가 안내와 구매 추천 요청의 범위 안내를 확인했다. 390px에서도 페이지 가로 넘침 없이 입력·답변·근거를 표시했다.
- 시험 계정의 내 제품에 실제 이력 API로 수리 기록을 등록한 뒤, 내 제품 Q&A가 `2026-10-20`과 실제 이력 `#4`를 근거로 답하고 세부 내용 미검토를 표시하는지 확인했다. 미검토 본문은 답변 근거에 포함되지 않았다. 이 계정·제품·이력은 복제 시험 DB에만 생성했다. `qa.localhost`의 별도 로그인 쿠키로 기존 `localhost`·8080 로그인을 바꾸지 않았다.

## 직접 확인

1. 18082에 로그인하고 `내 제품 → 제품 여권` 또는 내 판매글의 공개 상세를 연다.
2. `제품 이력에 질문하기`에서 현재 메모리·보증 만료일·수리 기록을 각각 질문한다.
3. 답변 아래 근거를 펼쳐 DB에 등록한 사양·이력 번호·날짜와 맞는지 확인한다. 이력이 없으면 확인 불가 안내가 정상이다.
4. `구매 추천해줘`, `시리얼 알려줘`에는 판단·정보 제공 불가 안내가 나오는지 확인한다.
5. 다른 회원에게는 내 제품 질문이 404이고, 공개 판매글 질문은 허용되는지 확인한다. SOLD/CANCELLED 글 질문은 404이며 현재 소유자의 내 제품 질문은 계속 허용된다.

이 구현은 main에 병합된 #59의 후속 변경이다. 검증은 별도 복제 DB·18082 서버에서 수행했으며 기존 개발 DB와 8080 서버를 변경하지 않았다. API 키·시험 계정·DB 덤프·로컬 실행 파일·화면 검증 이미지는 저장소에 포함하지 않는다.

실제 모델의 정정·무효·미검토·자료 누락 답변을 반복 확인하는 선택 실행 검사는 [제품 AI 실제 모델 품질 확인](AI_LIVE_QUALITY.md)을 따른다. 기존 HTTP 테스트와 달리 외부 Gemini를 호출하므로 실행 여부와 결과를 구분한다.
