# 이력 → 판매글·AI 공개 내용 연결 기준

## 서비스 정책

판매 중·예약 중인 판매글에서는 이전 소유자의 기록을 포함한 누적 핵심 이력을 제공한다. 판매자가 불리한 이력만 선택해서 숨길 수 없으며 정정·무효 기록도 남긴다. 문서 파일은 현재 소유자만 열람하고 소유권 이전 후 새 소유자에게 권한이 이어진다. 판매글 게시로 문서 권한은 바뀌지 않는다.

HIST-05의 공개 검토는 서버의 공개 필드 검사로 연결한다. ADMIN의 수동 승인 화면·승인 API·검토 대기 업무는 추가하지 않는다. 기존 관리자 기능은 조회 전용 범위를 유지한다.

## 현재 연결

ListingPublicationService는 소유권 검사와 제품 잠금 아래 ListingHistoryReader를 읽는다. 소유자용 원문 응답을 판매글에 그대로 재사용하지 않는다. JdbcListingHistoryReader와 ListingHistoryAdapter.read는 같은 SQL·자동 검사 규칙을 사용한다.

| 자료 | 판매글 전달 |
|---|---|
| 이력 유형·발생일·유효/무효·이전 소유자 여부 | 전체 누적 이력에서 제공 |
| 제목·내용·업체·교체 부품 | 공개 필드 자동 검사를 거쳐 제공 |
| 정정·무효 기록의 ID·시각·사유 | 전체 기록을 유지하고 사유는 개별 검사 |
| 시스템 소유권 이전 | 당사자 정보 없이 유형·날짜·상태만 제공 |
| 비용·시리얼·소유자 계정·문서·문서 등록 여부·감사 전후 원문 | 제공하지 않음 |

제목·본문·업체·부품은 서로 독립적으로 검사한다. 예를 들어 제목 ‘배터리 교체’, 본문 ‘담당자 홍길동 010-1234-5678’, 업체 ‘공식 서비스센터’, 부품 ‘배터리’라면 본문만 null로 제외하고 나머지를 제공한다. 이력 자체는 삭제하거나 누락하지 않는다. 사용자 원본과 소유자용 조회 결과도 변경하지 않는다.

public_text_reviewed·public_reason_reviewed의 기존 값은 공개 조건으로 쓰거나 강제로 true로 바꾸지 않는다. 검사 결과는 읽기 DTO에서 만들며 별도 승인 DB 갱신·이행 SQL이 필요하지 않다. 신규 등록·정정·무효 처리 후에는 다음 조회에서 현재 내용을 다시 검사한다.

## 자동 제외 범위와 한계

PublicHistoryTextPolicy는 길이·유니코드 호환 문자를 확인하고 전화번호·이메일·주민번호·카드 형태·긴 숫자 식별값·금액·URL·시리얼/계좌/주문/증빙 표시·이름/담당자 표시·주소 형태·HTML/제어 문자가 감지된 필드 전체를 제외한다. 해당 부분만 지운 뒤 나머지가 안전하다고 가정하지 않는다.

이는 규칙 기반 자동 검사이며 모든 자유문장의 실명·주소를 완벽하게 판별하는 개인정보 탐지기가 아니다. 표식 없이 쓴 임의의 이름, 새로운 우회 표현은 놓칠 수 있고 정상 문구가 보수적으로 제외될 수도 있다. 실제 이력 입력 예시를 이력 담당과 공유해 규칙을 보강한다. 입력 화면도 제품 사실만 적도록 안내해야 하며 이 작업이 수리 사실·품질·정품을 인증하지는 않는다. 문서의 사용자 마스킹 확인과 이력의 공개 필드 검사는 별개다.

## 기존 응답 형식의 상태 의미

- reviewed=true는 원천의 공개 필드 검사 가능 여부다. 문자열은 DTO에서 독립적으로 다시 검사하므로 플래그만으로 우회할 수 없다.
- detailsStatus=REVIEWED: 자동 검사 후 공개 가능한 내용이 있다. ADMIN 승인 상태가 아니다.
- detailsStatus=EXCLUDED: 공개 가능한 상세가 없거나 사유가 제외됐다. 화면은 계속 검토 대기라고 표시하지 않는다. 유형·날짜·정정·무효 표시는 유지한다.
- REVIEW_PENDING: 상세 컬럼이 없는 구형 원천 또는 상세 검사를 제공하지 않는 공급자다. 정상 스키마에서 과거 검토 플래그가 false라는 이유로 이 상태가 되지 않는다.
- READY와 빈 목록은 실제 이력이 없는 경우이며 UNAVAILABLE과 구분한다. 미배포 원천이나 조회 한도 초과를 빈 이력으로 바꾸지 않는다.

AI에는 같은 공개 DTO에서 유효 이력의 제목·내용·교체 부품을 제공한다. 무효 이력의 존재·날짜·상태는 유지하되 자유입력 본문을 실제 제품 사실로 사용하지 않는다. 업체·사유·감사 원문·문서·비용·계정은 AI 입력에 추가하지 않는다.

이력 등록·정정·무효 처리의 기존 facts_version 증가와 ProductFactsChanged / AFTER_COMMIT 갱신 경계를 유지한다. 카드 요약은 입력 정책 버전 2로 구분해 과거 메타데이터 전용 요약을 숨기고 기존 갱신 작업에서 새 입력으로 다시 생성한다. 기존 Flyway는 수정하지 않는다.

## 팀 연결 기준

이력 담당은 기존 이력 등록·정정·무효 API와 원본 저장을 유지한다. 판매글·AI 담당은 공개용 Reader의 자동 검사 결과만 사용한다. 별도 ADMIN 승인 API나 수동 불리언 변경은 필요하지 않다. 공개 제외 규칙을 바꿀 때에는 안전한 내용의 표시와 비공개 값 제외를 함께 검사한다.

소유권·판매 상태·문서 열람 권한은 각 기존 서비스가 계속 검사한다. 판매글 종료 시 일반 회원의 상세·이력·Q&A 접근을 종료하며 현재 소유자의 제품 관리는 유지한다. 미리보기나 AI 생성은 이력의 PUBLIC/PRIVATE 상태를 변경하지 않는다.

## 검증 기록 (2026-11-01)

- 최신 main `28bf630`의 로그인·AI 근거 보호·이력 화면 변경과 통합했다. 공개 필드 규칙·두 실제 SQL Reader·전달 DTO·이력 HTTP·질문 HTTP·서버 답변 구성의 관련 124건이 통과했다. 과거 검토 불리언이 false여도 안전한 상세가 제공되고, true여도 공개 제외 내용을 우회하지 못하는지 확인했다.
- 실제 이력 정정·무효 → 구매자 판매글 상세 → AI 입력 갱신을 검사했다. 이전 소유자 이력과 모든 정정 기록을 유지하며, VOID 본문은 AI 사실 입력에서 제외한다. 구매자의 문서 목록 요청은 403, 현재 소유자는 200을 확인했다.
- 기존 형식 버전 1의 카드 요약은 새 입력 정책으로 재생성하고, 버전 2 생성 후에는 같은 자료를 반복 갱신하지 않는지 확인했다.
- Java 전체 1,096건 중 985건 통과·환경 조건 제외 111건·실패/오류 0건. spotlessCheck test build 성공. 무효 이력이 함께 조회되는 경우에도 유효 이력의 자동 검사된 공개 상세는 답변과 근거에 유지한다.
- 화면 동작 검사 93건 통과. 공개 내용의 텍스트 표시와 제외 사유 안내를 DOM 대역으로 확인했다. 실제 브라우저 레이아웃을 검사한 결과는 아니다.
- API·DB 자동 검사는 격리 H2와 운영 Flyway를 사용했다. 외부 AI·Redis 실행권은 시험 대역이며 이 자동 검사에서 실제 Gemini 호출과 별도 PostgreSQL 실행은 하지 않았다. 공용 DB·기존 마이그레이션·개인 계정 변경은 포함하지 않는다. 로컬 실행 설정·계정·키·서버 로그는 PR에 포함하지 않는다.
